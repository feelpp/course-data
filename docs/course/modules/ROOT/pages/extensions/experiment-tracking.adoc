Experiment tracking is a structured record of what produced a result. It does not require a cloud service or personal account. Begin with a local, versioned record that another person can inspect and reproduce.

== Minimum run record

[source,json]
----
{
  "run_id": "air-quality-ridge-001",
  "code_commit": "<git commit>",
  "environment_lock_sha256": "<checksum>",
  "dataset_id": "uci-501-teaching-v1",
  "split_id": "chronological-cutoff-2016-01-01",
  "seed": 20260718,
  "parameters": {"model": "ridge", "alpha": 1.0},
  "metrics": {"validation_mae": 18.2},
  "artifacts": ["result-card.md", "residuals.parquet"]
}
----

The record must distinguish configuration chosen before fitting, validation evidence used for selection, and untouched final evidence. A tracker cannot rescue an invalid split or a missing dataset licence.

== Exercise

Wrap one core notebook experiment with a local JSON run record. Validate it against a small schema, calculate checksums for the environment lock and result artifact, and write an index that compares runs without overwriting them. Restart from a clean clone and reproduce one selected run.

Do not commit access tokens, direct personal identifiers, confidential paths, or unrestricted copies of large artifacts. Use the university-approved storage boundary where data cannot be published.

== When a service is justified

A shared service becomes useful when several people need search, lineage, access control, artifact retention, and comparison across many runs. The selection must follow privacy, security, cost, export, and deletion requirements. Full deployment orchestration remains P3 and is outside this course.
