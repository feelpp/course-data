This session starts from a simple question: *what does one row represent?* We call that the *unit of observation*. The closely related phrase *unit of analysis* means the kind of thing about which we calculate and report a result. It might be one sensor at one time, one patient, or one simulation run. Selecting rows, changing the table layout, calculating a summary, or joining another table must not silently change that meaning.

A table that looks plausible can still be wrong. A join can duplicate measurements, a missing value can disappear from a count, or a column containing numbers can mix different physical units. We therefore learn each pandas operation together with a small check.

== Rules to check for a table

A *tidy table* has one observation per row, one variable per column, and one kind of observation per table. This is a useful layout for analysis, not a rule that every file must always be stored that way.

For a join, write the expected relationship first: one-to-one, one-to-many, many-to-one, or intentional many-to-many. In pandas, use `validate=` where possible, inspect whether keys are unique, show unmatched rows, and compare the keys before and after the join. Comparing only the number of rows is insufficient: one row can be lost while another is duplicated.

A pandas `dtype` tells us how values are stored, such as integer, floating-point number, text, or date-time. It does not give their scientific meaning. An integer may be an identifier; a floating-point number still needs a physical unit; text may represent a category or a time. Keep names, units, allowed categories, missing-value rules, and timezone information beside the code.

== Arrays: shapes, axes and reductions

Begin with three observations and two variables: temperature in degrees Celsius and relative humidity in percent. A NumPy array has no column names, so we must remember that column 0 is temperature and column 1 is humidity.

The shape `(3, 2)` means *3 rows and 2 columns*. Read `axis=0` as “move down the rows and leave one result per column”. Each column keeps its own unit. An average across temperature and humidity would mix degrees Celsius with percent and would have no useful physical interpretation.

[#tabular-array-bridge]
[%dynamic%open,python,fail-on-error=]
----
import numpy as np

values = np.array([[20.0, 50.0], [22.0, 60.0], [24.0, 70.0]])
column_means = values.mean(axis=0)
centred = values - column_means
warm_rows = values[values[:, 0] >= 22.0]
assert values.shape == (3, 2)
assert column_means.shape == (2,)
assert warm_rows.shape == (2, 2)
assert np.allclose(centred.mean(axis=0), [0.0, 0.0])
print("Column means [Celsius, percent]:", column_means)
print("Centred rows:", centred)
----

`values[:, 0]` means “all rows from column 0”. Comparing those temperatures with 22 produces the Boolean mask `[False, True, True]`. Using that mask keeps the last two rows.

The means are 22 degrees Celsius and 60 percent. Subtracting the length-two mean array from the three-by-two input is *broadcasting*: NumPy applies the same pair `[22, 60]` to every row. Broadcasting avoids a Python loop, but compatible shapes do not guarantee a meaningful calculation; the units must also make sense.

== A practical DataFrame inspection toolbox

A pandas `DataFrame` adds column names and an index to a rectangular table. Before calculating anything, inspect its size, names, stored types, missing values, and a few rows.

[#tabular-inspect-table]
[%dynamic%open,python,fail-on-error=]
----
import pandas as pd

weather = pd.DataFrame(
    {
        "station": ["A", "A", "B", "B"],
        "time_utc": ["08:00", "09:00", "08:00", "09:00"],
        "temperature_c": [20.0, 22.0, 18.0, None],
    }
)

print("shape:", weather.shape)
print("columns:", weather.columns.tolist())
print("types:\n", weather.dtypes)
print("missing values:\n", weather.isna().sum())
weather.head()
----

Notice two kinds of pandas feature:

* an *attribute* describes the current object and has no parentheses: `weather.shape`, `weather.columns`, `weather.dtypes`;
* a *method* performs an operation and has parentheses: `weather.head()`, `weather.isna()`, `weather.sort_values(...)`.

Useful first questions are collected below. `df` means any DataFrame.

[cols="2,3,4",options="header"]
|===
|Expression |What it returns |Question it answers
|`df.head()` / `df.tail()` |The first or last five rows. |What do actual rows and values look like?
|`df.shape` |A pair `(number of rows, number of columns)`. |How large is the table?
|`df.columns.tolist()` |The column names as a Python list. |Which variables are available?
|`df.dtypes` |The storage type of each column. |Which columns are numeric, text, or date-time?
|`df.info()` |A compact summary including non-missing counts and memory use. |Are types or missing values surprising?
|`df.isna().sum()` |The number of missing values in each column. |Where is information missing?
|`df["station"].nunique()` |The number of distinct station values. |How many stations occur?
|`df["station"].value_counts()` |The number of rows for every station. |Are groups balanced or unexpectedly repeated?
|`df.duplicated(key).sum()` |The number of repeated keys. |Does the proposed key really identify rows?
|===

`info()` prints its summary rather than returning a new table. `nunique()` counts different non-missing values, whereas `unique()` returns those values. These small distinctions matter when checking unfamiliar data.

== Select rows and columns explicitly

Square brackets select a column: `weather["station"]`. A comparison on that column produces one Boolean value per row. `.loc[rows, columns]` then uses a row mask and named columns.

[#tabular-select-table]
[%dynamic%open,python,fail-on-error=,output=table,table-caption="Available measurements from station A, sorted by time",table-description="Two station A rows remain after selecting the station, requiring an available temperature, choosing three named columns, and sorting by time."]
----
is_station_a = weather["station"].eq("A")
has_temperature = weather["temperature_c"].notna()

station_a = weather.loc[
    is_station_a & has_temperature,
    ["station", "time_utc", "temperature_c"],
].sort_values("time_utc")

station_a
----

Read the expression in this order:

. `eq("A")` marks rows whose station is A;
. `notna()` marks rows whose temperature is available;
. `&` means that both conditions must be true; each condition needs parentheses when written directly inside `.loc`;
. the list after the comma chooses the three output columns;
. `sort_values("time_utc")` orders the result without changing the values.

The result is a new DataFrame. Use `.copy()` when you plan to modify such a selection: `station_a = station_a.copy()`. This makes the intention clear and avoids ambiguous chained assignments.

=== Rename, remove, and create columns

The following small source table uses an unclear measurement name and contains two columns that are useful during data collection but are not needed in the analysis table.

[#tabular-rename-drop-assign]
[%dynamic%open,python,fail-on-error=,output=table,table-caption="A clearer analysis table created with rename, drop and assign",table-description="The source measurement is renamed with its unit, collection-only columns are removed, and Fahrenheit values are calculated without changing the source table."]
----
source_weather = pd.DataFrame(
    {
        "sensor_id": ["A", "B", "C"],
        "value1": [20.0, 22.0, 18.0],
        "unit": ["C", "C", "C"],
        "collection_note": ["checked", "checked", "checked"],
    }
)

# It is safe to put the unit in the column name only after checking it.
assert source_weather["unit"].eq("C").all()

analysis_weather = (
    source_weather
    .rename(columns={"sensor_id": "station", "value1": "temperature_c"})
    .drop(columns=["unit", "collection_note"])
    .assign(
        temperature_f=lambda df: df["temperature_c"] * 9 / 5 + 32,
        above_20_c=lambda df: df["temperature_c"] > 20,
    )
)

analysis_weather
----

Read the chain from top to bottom:

. `rename(columns={...})` changes the two column labels. The dictionary maps each old name to its new name.
. `drop(columns=[...])` removes columns from the result. Here the unit is no longer a separate column because it was checked and recorded in `temperature_c`; the collection note is not an analysis variable.
. `assign(...)` creates or replaces columns. Each `lambda df` receives the table produced by the preceding steps, so it can refer to the newly named `temperature_c` column.

These methods return a new DataFrame by default: `source_weather` is unchanged. This makes the sequence easier to inspect and avoids altering the raw input accidentally. A method call can still be valid Python while making a poor scientific choice, so explain why each renamed, removed, or calculated column is appropriate.

== Wide and long tables

In a *wide* table below, the station names A and B appear as column names. One row represents one time and contains both temperatures. In the *long* table, station becomes a variable: one row represents one station at one time.

Neither layout is universally better. Wide form is convenient for comparing aligned columns or displaying a report. Long form is usually convenient for grouping, plotting and applying the same operation to every station. The important question is what one row represents in each layout.

=== What does `melt` do?

`melt` turns selected columns into rows. It makes a table *longer and narrower*. Here is one row of the wide input:

[cols="1,1,1",options="header"]
|===
|`time_utc` |`A` |`B`
|08:00 |20.0 |18.0
|===

After melting columns `A` and `B`, that one row becomes two rows:

[cols="1,1,1",options="header"]
|===
|`time_utc` |`station` |`temperature_c`
|08:00 |A |20.0
|08:00 |B |18.0
|===

The transformation follows three simple rules:

. `time_utc` is an identifying column, so its value is repeated;
. the old column names `A` and `B` become values in a new `station` column;
. the values formerly stored under `A` and `B` go into a new `temperature_c` column.

Nothing is calculated, averaged, or discarded. Only the layout changes. With two input rows and two melted measurement columns, predict `2 × 2 = 4` output rows before running the code.

First construct and display the wide input. Each row represents one time, and the station names are column names.

[#tabular-wide-before-melt]
[%dynamic%open,python,fail-on-error=,output=table,table-caption="Wide input before melt",table-description="The wide input has two time rows and one Celsius column for each station."]
----
import pandas as pd

wide = pd.DataFrame(
    {
        "time_utc": ["08:00", "09:00"],
        "A": [20.0, 22.0],
        "B": [18.0, 20.0],
    }
)

wide
----

Now apply `melt` and display the long result. Each row represents one station at one time.

[#tabular-long-after-melt]
[%dynamic%open,python,fail-on-error=,output=table,table-caption="Long result after melt",table-description="The same four measurements now occupy four rows, keyed by station and time."]
----
long = wide.melt(
    id_vars="time_utc",
    var_name="station",
    value_name="temperature_c",
)

assert len(long) == 4
assert not long.duplicated(["station", "time_utc"]).any()
long
----

The arguments to `melt` say:

* `id_vars="time_utc"`: repeat this identifying column;
* `var_name="station"`: put the former column names A and B into a column named `station`;
* `value_name="temperature_c"`: put the four measurements into a column named `temperature_c`.

The values and units are unchanged; only the table layout and the meaning of one row change. The long-table key is `(station, time_utc)`, and the expected row count is `2 times × 2 stations = 4`.

`pivot` performs the reverse operation when every station-time key is unique:

[#tabular-pivot-back]
[%dynamic%open,python,fail-on-error=,output=table,table-caption="The four long observations returned to wide form",table-description="The unique station-time keys are rearranged so each time is a row and stations A and B are temperature columns."]
----
wide_again = (
    long.pivot(index="time_utc", columns="station", values="temperature_c")
    .reset_index()
    .rename_axis(columns=None)
)
assert wide_again.equals(wide)
wide_again
----

`pivot` refuses to continue if two rows have the same station-time key. That error is useful: it reveals a duplicate that requires a decision. `pivot_table` can combine duplicates with an operation such as `mean`, but this changes the data and should be used only when that aggregation answers the intended question.

== A small checked join

A join combines columns from two tables by matching a key. Here the measurement table has several rows per station, while the station table has exactly one description per station. The expected relationship is therefore *many measurements to one station description*.

[cols="1,1,1",options="header"]
|===
|`station` |`city` |`elevation_m`
|A |North |140
|B |South |85
|===

Before joining, check that `station` is unique in the description table. Then ask pandas to verify the expected relationship with `validate="many_to_one"`.

[#tabular-small-join]
[%dynamic%open,python,fail-on-error=,output=table,table-caption="Four measurements enriched with one description per station",table-description="Every station-time measurement is retained exactly once and receives its matching city and elevation."]
----
station_info = pd.DataFrame(
    {
        "station": ["A", "B"],
        "city": ["North", "South"],
        "elevation_m": [140, 85],
    }
)

assert station_info["station"].is_unique

enriched = long.merge(
    station_info,
    on="station",
    how="left",
    validate="many_to_one",
    indicator=True,
)

assert len(enriched) == len(long)
assert enriched["_merge"].eq("both").all()
enriched
----

Read the join arguments one by one:

* `on="station"` chooses the matching key;
* `how="left"` keeps every measurement row, even if its station has no description;
* `validate="many_to_one"` raises an error if the right table contains repeated station keys;
* `indicator=True` creates `_merge`, which says whether each row matched both tables or appeared on only one side.

[cols="1,3,3",options="header"]
|===
|`how=` |Rows kept |Typical use
|`"left"` |Every left row, plus matching right columns. |Enrich measurements while retaining all measurements.
|`"inner"` |Only keys present on both sides. |Keep matched cases, while accepting that unmatched rows disappear.
|`"outer"` |Every key from either side. |Diagnose missing matches on both sides.
|===

The four common `validate=` relationships are `"one_to_one"`, `"one_to_many"`, `"many_to_one"`, and `"many_to_many"`. Using `"many_to_many"` performs no uniqueness check, so reserve it for cases where repeated keys on both sides are deliberate and their multiplication has been predicted.

For example, duplicating station A in `station_info` would make the join above ambiguous. Because `validate="many_to_one"` is present, pandas raises a `MergeError` instead of silently duplicating both A measurements.

Before moving to the larger example, be able to answer four questions:

. What does one row of the left table represent?
. Which column or columns form its key?
. Which join relationship do we expect?
. Which counts, keys and `_merge` values should remain unchanged or be reported?

== Mathematical reference

For stem:[X\in\mathbb R^{n\times p}], rows index stem:[n] observations and columns index stem:[p] variables. A column mean is

[stem]
++++
\bar x_j=\frac1n\sum_{i=1}^{n}X_{ij},
++++

whereas a row mean averages different variables and often has no scientific meaning. Broadcasting a vector stem:[a\in\mathbb R^p] across rows produces stem:[Y_{ij}=X_{ij}+a_j]; the shape is valid only if this per-variable operation matches units and semantics.

.Definition: Join multiplicity
[.def#def:join-multiplicity]
****
For join key stem:[k], let stem:[m_L(k)] and stem:[m_R(k)] be its multiplicities in left and right tables. An inner equality join produces

[stem]
++++
N_{\mathrm{join}}=\sum_{k}m_L(k)m_R(k)
++++

rows. A key duplicated twice on each side produces four joined rows. The formula explains why an unintended many-to-many join can silently reweight later summaries.
****

== Aggregation and error

If group stem:[g] has stem:[n_g] observations and mean stem:[\bar x_g], the global mean is the size-weighted quantity

[stem]
++++
\bar x=\frac{\sum_g n_g\bar x_g}{\sum_g n_g},
++++

not the unweighted mean of group means unless all group sizes are equal or the question deliberately gives every group equal weight. Standard deviation describes variation among observations; standard error describes uncertainty in an estimated quantity such as a mean. Aggregating hourly measurements to daily means changes what one row represents and also changes which values depend on each other.

== Hand calculation: join amplification

.Example: Join amplification
[.examp#ex:join-amplification]
****
For key A, the left table has two rows and the right table three; for key B, each has one. The inner join contains stem:[2\times3+1\times1=7] rows. A mean computed after this join weights A six times and B once. If the intended unit was one key, the result answers the wrong question even though the merge succeeds.
****

=== Implementation

*Importance:* Essential (P0)

The implementation checks the observation key, predicts tidy multiplicity, requests a `many_to_one` join, and compares the complete key set before presenting any enriched rows.

[#validated-join-table]
[%dynamic%open,python,fail-on-error=,output=table,table-caption="Checked observation-to-station join",table-description="The first five joined rows retain the station and timestamp key, PM2.5 measurement, and source filename after an expected many-to-one join."]
----
from pathlib import Path

import pandas as pd

# These Antora attachment references become notebook-relative dataset paths.
def course_file(relative: str) -> Path:
    """Locate canonical data in a repository checkout or student bundle."""
    for root in [Path.cwd(), *Path.cwd().parents]:
        candidate = root / relative
        if candidate.is_file():
            return candidate
    raise FileNotFoundError(relative)


observations_path = course_file("datasets/teaching/air-quality/observations.csv")
stations_path = course_file("datasets/teaching/air-quality/stations.csv")
observations = pd.read_csv(observations_path)
stations = pd.read_csv(stations_path)


def prepare_tables(
    observations: pd.DataFrame, stations: pd.DataFrame
) -> tuple[pd.DataFrame, pd.DataFrame]:
    """Construct the observation key, tidy pollutants, and check the station join."""
    frame = observations.copy()
    frame["timestamp"] = pd.to_datetime(frame[["year", "month", "day", "hour"]])
    key = ["station", "timestamp"]
    if frame.duplicated(key).any():
        raise ValueError("Observation key is not unique")

    pollutants = frame.melt(
        id_vars=key,
        value_vars=["PM2.5", "PM10", "NO2"],
        var_name="pollutant",
        value_name="concentration",
    )
    before = set(map(tuple, frame[key].itertuples(index=False, name=None)))
    joined = frame.merge(
        stations, on="station", how="left", validate="many_to_one", indicator=True
    )
    after = set(map(tuple, joined[key].itertuples(index=False, name=None)))
    if before != after or not joined["_merge"].eq("both").all():
        raise ValueError("Join changed or failed to match observation keys")
    return joined.drop(columns="_merge"), pollutants


joined, pollutants = prepare_tables(observations, stations)
assert joined[["station", "timestamp"]].duplicated().sum() == 0
assert len(joined) == len(observations)
assert set(pollutants["pollutant"]) == {"PM2.5", "PM10", "NO2"}
assert len(pollutants) == 3 * len(observations)
joined[["station", "timestamp", "PM2.5", "source_file"]].head()
----
