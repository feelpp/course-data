Data quality means that a table is suitable for a stated use. It is not a generic “clean/dirty” label. The same extreme measurement may be a sensor failure, a rare event of scientific interest, or a valid observation that strongly affects a result.

After reading the audit route and examples on this page, work through xref:foundations/data-quality-practical.adoc[Guided practical: audit a complete air-quality dataset]. The companion notebook follows all 1,008 station-hour observations from file verification to a documented quality report in a two-hour session.

Read the opening of xref:foundations/mathematical-background.adoc#_data_population_and_notation[Mathematical background: data, population, and notation] first. It defines an observation, a sample, a population, and an empirical mean. This page then shows how missing values, duplicates, and unusual values change the observations available for a calculation. Formal missingness notation and robust anomaly scores are kept on the xref:foundations/mathematical-background.adoc#_missingness_indicators_and_mechanisms[mathematical background page] so that the practical audit remains readable.

== A repeatable audit route

Use the same five steps for every quality question:

. *State the intended use.* A missing temperature may prevent a mean calculation but may be harmless when counting station identifiers.
. *State what one row represents and its key.* Without this, a repeated row cannot be classified as valid or duplicated.
. *Count and display the affected rows before changing anything.* A total count alone can hide concentration in one station or time period.
. *Choose an action and explain it.* Keep, correct, remove, or quarantine a value only for a stated reason. Here, *quarantine* means excluding it from calculations while preserving the original value for review.
. *Run the same checks again.* Report what changed and what remains unresolved.

== Audit dimensions

[cols="2,4,4",options="header"]
|===
|Dimension |Question |Example check
|Identity |Is each unit represented exactly as intended? |Non-null/unique key and join-cardinality checks.
|Completeness |What is missing, where, and under what process? |Missingness by time, station, group, target, and feature.
|Validity |Do values obey type, unit, category, and domain rules? |Schema assertions and explicit conversion rules.
|Consistency |Do related fields and tables agree? |Cross-field, temporal, and referential checks.
|Plausibility |Are extremes errors, rare valid events, or influential cases? |Domain review, robust summaries, sensitivity analysis.
|Timeliness/provenance |Does the artifact represent the intended version and decision time? |Source, checksum, retrieval/version, event-time record.
|===

== Schemas: write the rules before inspecting values

A schema is a written description of the table structure and its allowed values. It turns expectations into checks that can be rerun. Write these rules before looking for surprising results; otherwise it is tempting to adapt a rule merely to make the current table pass.

[cols="2,3,3",options="header"]
|===
|Column or key |Declared rule |Useful check
|`station` |Non-missing text drawn from the station registry. |`notna()` and membership in the registry.
|`time_utc` |A date and time interpreted in UTC. |Parse as a timezone-aware date-time and report failures.
|`temperature_c` |A number measured in degrees Celsius. |Numeric conversion, explicit unit, and a domain-informed review range.
|`wind_direction` |One of the declared compass categories, or missing. |`isin(allowed_directions)` for non-missing values.
|`(station, time_utc)` |At most one intended observation per station and time. |`duplicated(["station", "time_utc"])` followed by review of every match.
|===

A schema failure identifies a row to investigate. It does not always prescribe a repair. For example, a temperature outside a review range may be a valid extreme, whereas a failed date-time conversion indicates that the program cannot yet interpret the recorded value.

== Missing values

Do not begin by filling empty cells. First ask where the values are missing and how the measuring process could have produced that pattern.

. Detect missing values with `isna()` and count them with `sum()`.
. Compare counts by station, device, group, or time period.
. Display the affected rows together with useful context.
. Ask how the value became missing.
. Decide whether to keep it missing, recover it from a trusted source, exclude a row for a particular calculation, or later estimate it with an explicit model.

The small table below has the same overall number of records for stations A and B, but missingness is concentrated differently.

[#quality-missing-by-station]
[%dynamic%open,python,fail-on-error=,output=table,table-caption="Missing temperatures by station",table-description="Both stations have three records, while station B has twice as many missing temperatures as station A."]
----
import pandas as pd

measurements = pd.DataFrame(
    {
        "station": ["A", "A", "A", "B", "B", "B"],
        "time_utc": ["08:00", "09:00", "10:00"] * 2,
        "temperature_c": [20.0, None, 22.0, 18.0, None, None],
    }
)

missing_by_station = (
    measurements.groupby("station", as_index=False)
    .agg(
        records=("temperature_c", "size"),
        missing=("temperature_c", lambda values: values.isna().sum()),
    )
    .assign(missing_rate=lambda df: df["missing"] / df["records"])
)

missing_by_station
----

The overall rate is `3 / 6 = 0.50`, but it hides the difference between station A (`1 / 3`) and station B (`2 / 3`). Investigate that difference before calculating a mean or filling values.

Using the missingness indicator defined on the preceding mathematical page, this example applies the empirical-rate formula as

[stem]
++++
\widehat p_{\mathrm{missing}}
=\frac{\text{number of missing values}}{\text{number of rows}}
=\frac{3}{6}=0.50.
++++

The calculation is simple; deciding whether this overall rate adequately describes both stations is the substantive question.

=== Missingness mechanisms, with examples

The names MCAR, MAR, and MNAR describe possible *processes* that produce missing values. They are not conclusions returned automatically by pandas.

[cols="1,3,3",options="header"]
|===
|Name |Concrete example |What to investigate
|MCAR: unrelated to recorded or missing values |A connector is accidentally unplugged at a randomly chosen time, independently of station and temperature. |Maintenance notes and whether outages are spread across stations, times, and values.
|MAR: explained by recorded information |An older device model loses more messages; the device model is recorded in the table. |Missing rates by the recorded device model and other observed groups.
|MNAR: related to the value that is missing |A temperature sensor saturates above its limit, so the highest unrecorded temperatures are most likely to be missing. |Sensor limits, external measurements, and results under several plausible values for the missing high temperatures.
|===

The mechanism cannot usually be identified from the incomplete table alone. Domain knowledge about the sensor, form, database, or collection procedure is required. See xref:foundations/mathematical-background.adoc#_missingness_indicators_and_mechanisms[Missingness indicators and mechanisms] for the formal probability definitions.

Replacing missing values merely to satisfy an API is not a repair. Dropping rows can change the population represented by the table; filling with a constant or mean changes the distribution; predictive filling adds modelling assumptions. A learned filling method must be fitted only on training data, and a missing target is not silently invented.

== Duplicates

A duplicate can mean three different things:

* an *exact ingestion duplicate*: the same record was copied twice;
* a *valid repeated event*: the same station produced a new observation at another time;
* a *conflicting record*: two rows claim the same key but disagree on a value.

The key, rather than visual similarity, determines which case needs investigation.

[#quality-duplicate-types]
[%dynamic%open,python,fail-on-error=,output=table,table-caption="Exact duplicates and conflicting keys",table-description="Two A rows are exact copies, while two B rows share a station-time key but contain conflicting temperatures."]
----
records = pd.DataFrame(
    {
        "station": ["A", "A", "A", "B", "B"],
        "time_utc": ["08:00", "08:00", "09:00", "08:00", "08:00"],
        "temperature_c": [20.0, 20.0, 21.0, 18.0, 19.0],
    }
)

key = ["station", "time_utc"]
duplicate_review = records.assign(
    exact_duplicate=records.duplicated(keep=False),
    repeated_key=records.duplicated(key, keep=False),
)

duplicate_review
----

The two identical A–08:00 rows may be reduced to one if their provenance confirms an ingestion copy. The A–09:00 row is a new event and must remain. The B–08:00 rows conflict: `drop_duplicates(key)` would keep one temperature arbitrarily, so they must be compared with the source or quarantined. Always declare the key and the resolution rule before calling `drop_duplicates()`.

== Anomalies

An anomaly is a value worth investigating. It is not automatically an error. Work through these questions in order:

. Is the value stored in the expected type and unit?
. Is it attached to the correct station, time, patient, or experiment?
. Does it violate a physical or administrative limit?
. Is it unusual only globally, or also within its station, season, or experimental condition?
. Does keeping or excluding it materially change the conclusion?

[cols="2,3,3",options="header"]
|===
|Observed value |Investigation |Defensible action
|`71.6` among Celsius temperatures |Metadata records this row in Fahrenheit; `71.6 °F = 22 °C`. |Convert it and record the conversion.
|`45 °C` during a documented heat experiment |The value is rare but the unit, sensor range, and experimental context agree. |Keep it and report that it is influential.
|`-2 m/s` wind speed |A speed cannot be negative and the source offers no correction. |Quarantine it as missing and retain the original row for review.
|===

A boxplot or a large robust score only flags a value for review. It does not choose the action. The median absolute deviation and its formula are explained in xref:foundations/mathematical-background.adoc#_robust_summaries_and_anomaly_flags[Robust summaries and anomaly flags].

== Consequences for analysis

=== Sensitivity analysis

After the operational audit, repeat the main calculation under several defensible choices. For example, retain or quarantine a disputed anomaly, analyse complete rows or relevant subgroups, and use more than one plausible treatment for missing values. A change across these choices reveals that the conclusion depends on the quality policy; the range is not automatically a confidence interval.

Uncertainty formulas for missing rates and deterministic unit conversions belong to xref:foundations/mathematical-background.adoc#_uncertainty_for_quality_measurements[Uncertainty for quality measurements].

== Worked example: audit, repair, and quarantine

=== Context

[.worked-example-method#worked-quality-method]
=== Method

*Importance:* Essential (P0)

. Declare the observation key and admissible wind categories before inspecting results.
. Count every violation without altering the input table.
. Convert the row whose Fahrenheit unit is explicitly recorded.
. Remove the exact duplicate, but preserve the identity rule used to detect it.
. Quarantine invalid wind values and rerun the identical audit to produce the before/after table.

For each rule stem:[r], the reported value is the explicit count stem:[c_r=\sum_{i=1}^{n}\mathbf 1\{\text{row }i\text{ violates }r\}]. The before/after comparison is meaningful because the same function and denominator are used on both tables.

[.worked-example-implementation#worked-quality-implementation]
=== Implementation

*Importance:* Essential (P0)

The implementation introduces known defects, applies the same audit before and after justified repairs, and converts unresolved anomalies to explicit missing values.

[#quality-audit-table]
[%dynamic%open,python,fail-on-error=,output=table,table-caption="Quality findings before and after justified deterministic repair",table-description="Rows identify duplicate keys, missing PM2.5 values, non-Celsius rows, invalid wind categories, and negative wind speed. Columns compare issue counts before and after repair."]
----
from pathlib import Path

import pandas as pd

def course_file(relative: str) -> Path:
    """Locate canonical data in a repository checkout or student bundle."""
    for root in [Path.cwd(), *Path.cwd().parents]:
        candidate = root / relative
        if candidate.is_file():
            return candidate
    raise FileNotFoundError(relative)


data_path = course_file("datasets/teaching/air-quality/observations.csv")
clean = pd.read_csv(data_path).head(80)

# Add controlled defects without changing the reviewed source file.
quality = clean.copy()
quality["temperature_unit"] = "C"
quality.loc[3, ["TEMP", "temperature_unit"]] = [quality.loc[3, "TEMP"] * 9 / 5 + 32, "F"]
quality.loc[7, "wd"] = "INVALID"
quality.loc[11, "WSPM"] = -2.0
quality = pd.concat([quality, quality.iloc[[5]]], ignore_index=True)


def audit_quality(frame: pd.DataFrame) -> dict[str, int]:
    """Count violations without silently changing the data."""
    key = ["station", "year", "month", "day", "hour"]
    valid_wind = {
        "N", "NNE", "NE", "ENE", "E", "ESE", "SE", "SSE",
        "S", "SSW", "SW", "WSW", "W", "WNW", "NW", "NNW",
    }
    return {
        "duplicate key rows": int(frame.duplicated(key, keep=False).sum()),
        "missing PM2.5": int(frame["PM2.5"].isna().sum()),
        "non-Celsius rows": int(frame["temperature_unit"].ne("C").sum()),
        "invalid wind category": int((frame["wd"].notna() & ~frame["wd"].isin(valid_wind)).sum()),
        "negative wind speed": int(frame["WSPM"].lt(0).sum()),
    }


before = audit_quality(quality)
assert before["duplicate key rows"] == 2
assert before["non-Celsius rows"] == 1
assert before["invalid wind category"] == 1
assert before["negative wind speed"] == 1

# Convert the known Fahrenheit row, resolve the exact duplicate, and quarantine
# invalid categorical/numeric values as missing for later modelling decisions.
repaired = quality.copy()
is_fahrenheit = repaired["temperature_unit"].eq("F")
repaired.loc[is_fahrenheit, "TEMP"] = (repaired.loc[is_fahrenheit, "TEMP"] - 32) * 5 / 9
repaired.loc[is_fahrenheit, "temperature_unit"] = "C"
repaired = repaired.drop_duplicates(["station", "year", "month", "day", "hour"])
valid_observed_wind = set(clean["wd"].dropna().unique())
repaired.loc[~repaired["wd"].isin(valid_observed_wind), "wd"] = pd.NA
repaired.loc[repaired["WSPM"].lt(0), "WSPM"] = pd.NA
after = audit_quality(repaired)

pd.DataFrame({"before repair": before, "after repair": after})
----

=== Results

*Importance:* Essential (P0)

The repeated audit shows that duplicate keys, the known unit mismatch, the invalid wind category, and the negative wind speed are removed or quarantined by the declared operations. Missing PM2.5 values remain visible rather than being silently completed, so the table distinguishes repair from unresolved missingness.

[.worked-example-conclusion#worked-quality-conclusion]
=== Conclusion

*Importance:* Essential (P0)

The deterministic repairs satisfy the declared table rules, but they do not prove that every unusual measurement is wrong. The remaining missing values are intentional quarantine markers, not completed repairs. Any imputation is learned inside a training pipeline, and a domain reviewer must decide whether the wind anomalies are sensor errors or valid exceptional events. Measurement error, undocumented unit changes, and population coverage remain outside this audit.
