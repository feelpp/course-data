Data quality is fitness for a stated use, not a generic “clean/dirty” label. The same extreme measurement may be a sensor failure, a rare event of scientific interest, or an influential but valid observation.

== Audit dimensions

[cols="2,4,4",options="header"]
|===
|Dimension |Question |Executable evidence
|Identity |Is each unit represented exactly as intended? |Non-null/unique key and join-cardinality checks.
|Completeness |What is missing, where, and under what process? |Missingness by time, station, group, target, and feature.
|Validity |Do values obey type, unit, category, and domain rules? |Schema assertions and explicit conversion rules.
|Consistency |Do related fields and tables agree? |Cross-field, temporal, and referential checks.
|Plausibility |Are extremes errors, rare valid events, or influential cases? |Domain review, robust summaries, sensitivity analysis.
|Timeliness/provenance |Does the artifact represent the intended version and decision time? |Source, checksum, retrieval/version, event-time record.
|===

== Missing values

First report the pattern and context. Do not replace missing values merely to satisfy an API. Dropping can change the population; constant or statistical imputation changes distributions; predictive imputation adds modelling assumptions. Any learned imputer is fitted only on training folds through the pipeline. The target is not silently imputed.

== Duplicates and anomalies

Separate exact ingestion duplicates from repeated events and conflicting records. Never call `drop_duplicates()` without a declared identity and resolution policy. Likewise, never delete an outlier only because a boxplot labels it: verify unit, sensor range, event context, leverage, and conclusion sensitivity.
